## บริการกลับมารันภายใต้ systemd แล้ว (ปิดจุดเสี่ยงชั่วคราวแล้ว)

ระหว่าง deploy ต้อง restart `qwen-draw@ekkaphap.service` แต่ตอนแรก `sudo` ต้องใช้รหัสผ่าน จึงรัน `draw_server.py` ด้วยมือชั่วคราว ภายหลังได้รหัส sudo แล้วจัดการเรียบร้อย:

1. ปิด process มือด้วย `pkill` (พอร์ต 8190 ว่าง — ระวัง `pkill -f` match คำสั่งของ session ตัวเองทำให้ ssh หลุด ใช้ pattern แบบ `[d]raw_server` กันพลาด)
2. `echo <รหัส> | sudo -S systemctl start qwen-draw@ekkaphap`
3. สถานะ `active (running)` (Main PID 355313 ตอน start) โหลด drop-in `override.conf` ครบ
4. ตรวจซ้ำ: `/` 200, `/approve` 200, `POST /api/register` body ว่าง → 400 และผ่านโดเมนจริงเห็นฟอร์ม username + แท็บจัดการเนื้อหา

**บทเรียนสำหรับ deploy ครั้งหน้า:** การ kill main process ของ unit นี้ทำให้ python ออกแบบ clean exit → systemd มองว่าสำเร็จ → `Restart=on-failure` ไม่ทำงาน อย่าใช้วิธี kill เพื่อ restart; ใช้ `sudo systemctl restart qwen-draw@ekkaphap` ตรงๆ หรือถ้าจะ kill จริง ให้ตามด้วย `sudo systemctl start` เสมอ และอย่าปล่อย process มือค้างไว้ (systemd จะ start ไม่ขึ้นเพราะ `Address already in use` — สาเหตุ crash-loop 683 รอบของวันที่ 4 ต.ค.)

## สิ่งที่เปลี่ยนในเวอร์ชันนี้

- **บัญชีผู้ใช้จริง**: หน้าแรกล็อกอินด้วย username + password (ไม่ใช่รหัสร่วมอีกต่อไป) พร้อมลิงก์สมัครใช้งาน (ชื่อ-นามสกุล / username / password; username ห้ามว่าง-ห้ามซ้ำ-รูปแบบ `[a-z0-9._-]{3,32}`, password ห้ามว่าง) — คำขอใหม่เป็นสถานะ pending, ล็อกอินไม่ได้จนกว่าจะอนุมัติ (403)
- **หน้าอนุมัติ `/approve`** (ไฟล์ `approve.html`): ปลดล็อกด้วยรหัส `thanipitak1` (`APPROVE_CODE`, รับ `DRAW_PASSWORD` เดิมเป็น fallback) แล้วกดอนุมัติ/ปฏิเสธคำขอ pending
- **คลังเนื้อหา 50MB/คน** (`USER_QUOTA_MB`): ข้อมูลอยู่ที่ `user_data/` (`THANIPITAK_DATA_DIR`) — บัญชีและแชตใน SQLite `users.db`, ไฟล์ใน `users/<username>/images|music` ชื่อไฟล์ตามสเปก `<username>+picture-thanipitak.png` และ `<username>+music-thanipitak.mp3` (ไฟล์ถัดไป `-2`, `-3`)
- **เก็บอัตโนมัติ**: ทุกคำถาม-คำตอบใน webchat ลง DB (แท็บแชตมีแถบประวัติด้านซ้าย คลิกเปิดซ้ำได้, `＋ แชตใหม่` เริ่มเซสชันใหม่); รูป/เพลงที่สร้างเสร็จถูกคัดลอกเข้าคลังของเจ้าของงานทันที (ถ้าโควต้าเต็ม งานยังสำเร็จ แต่หน้าเว็บเตือนว่าไม่ได้เก็บ)
- **แท็บ "🗂 จัดการเนื้อหา"**: กราฟพื้นที่ใช้ไป/คงเหลือ + ลบแชต/รูป/เพลงรายชิ้นหรือล้างทั้งชุด (ลบแล้วคืนโควต้าทันที); chip "💾 x.x / 50 MB" บนหัวเว็บแสดงพื้นที่ตลอดเวลา
- รหัสผ่านเก็บแบบ PBKDF2-HMAC-SHA256 200,000 รอบ + salt ต่อบัญชี; รหัสผิดถูกหน่วง 0.8 วินาที
- Endpoint ใหม่: `POST /api/register`, `POST /api/approve/login`, `GET /api/admin/pending`, `POST /api/admin/approve|reject`, `GET /api/storage`, `GET /api/library`, `GET /api/chats/<id>`, `GET /api/media/<id>/file`, `DELETE /api/chats[/<id>]`, `DELETE /api/media[/<id>][?kind=]`
- `/api/status/<id>` ไม่ส่อง `user_id`/`username` ของเจ้าของงานแล้ว; ไฟล์ในคลังดึงได้เฉพาะเจ้าของเท่านั้น

## ผลตรวจหลัง deploy (ผ่าน Cloudflare, User-Agent แบบ browser)

- `GET /` → 200 พร้อมฟอร์ม username + แท็บจัดการเนื้อหา; `GET /approve` → 200
- `POST /api/login` สไตล์เก่า (รหัสร่วม) → 400 (ต้องใช้ username แล้ว)
- Flow เต็มบน production: สมัคร `smoketest-tmp` → ล็อกอินตอน pending ได้ 403 → ปลดล็อกด้วยรหัส → เห็นในรายการ pending → อนุมัติ → ล็อกอินสำเร็จ → `/api/storage` รายงานโควต้า 52,428,800 bytes → ลบบัญชีทดสอบออกจาก DB แล้วล็อกอินซ้ำได้ 401 (ฐานข้อมูลสะอาด)
- หมายเหตุ: คำขอจาก `Python-urllib` default UA โดน Cloudflare 403 — ตรวจ API ผ่านโดเมนต้องตั้ง User-Agent แบบเบราว์เซอร์ (เจอมาแล้วใน deploy ก่อนหน้า)
- `comfyui`, `cloudflared` ยัง `active`; คิว ComfyUI ว่างขณะ restart
